## 1. 初期セットアップの流れ

初めて導入するときは以下の順序で設定します。

```
① Microsoft Entra ID にアプリを登録する
      ↓
② 商工会議所メール配信システム（部会版）をインストールする
      ↓
③ 初回起動時に「会」（女性部・青年部など）と接続先データベースを登録する
      ↓
④ アプリの設定タブで接続情報を入力・保存する
      ↓
⑤ 担当者（職員）を登録する
      ↓
⑥ テスト送信で動作確認する
      ↓
（会を増やす場合）⑦「ファイル」→「会を切り替える…」→「会を追加」で③〜⑥を繰り返す
      ↓
（複数台運用の場合）⑧ PostgreSQL を構築し、各PCで接続設定を変更する
```

> **④〜⑥は会ごとに必要です。** 会を追加するときは「設定の引き継ぎ元」で既存の会を選ぶと、
> Microsoft 365の接続情報（テナントID・クライアントID等）を引き継げます。
> 名簿・会議・送信履歴などのデータは引き継がれません（会ごとに独立します）。

## 2. Microsoft Entra ID の設定

本システムはメール送信に **Microsoft Graph API** を使用します。  
送信元となる Microsoft 365 テナントで、アプリを登録して認証情報を取得します。

> **重要：** 本システムは「委任されたアクセス許可」によるユーザーサインイン方式を採用しています。クライアントシークレットは使用せず、実際にメールを送信する担当者本人が、送信操作のたびに（初回のみ、以降は端末に記憶）Microsoft 365 アカウントでサインインします。代理差出人アドレスを未設定の場合、送信元はサインインした担当者本人です。共通の代表メールアドレスから送信する場合は、各担当者に共有メールボックス／代表アドレスの「Send As」権限を付与し、`Mail.Send.Shared` を追加する必要があります。

> **前提：** Microsoft 365 のグローバル管理者またはアプリケーション管理者のアカウントが必要です（アプリ登録作業のみ）。

### 2-1. Azure ポータルにサインイン

ブラウザで [https://portal.azure.com](https://portal.azure.com) を開き、  
Microsoft 365 の管理者アカウントでサインインします。

### 2-2. Microsoft Entra ID を開く

ポータル上部の検索欄に「**Entra ID**」と入力し、「Microsoft Entra ID」をクリックします。

### 2-3. アプリの登録

1. 左メニューの「**アプリの登録**」をクリック
2. 「**新規登録**」をクリック

   | 項目 | 入力内容 |
   |------|----------|
   | 名前 | 例：`商工会議所メール配信システム` |
   | サポートされるアカウントの種類 | **この組織ディレクトリのみのアカウント** を選択 |
   | リダイレクト URI | 入力不要（次の手順で追加します） |

3. 「**登録**」をクリック

### 2-4. テナントIDとクライアントIDを控える

登録後の「概要」画面に以下が表示されます。  
**必ずメモしておいてください。**

| 表示名 | アプリ設定での呼び方 |
|--------|-------------------|
| アプリケーション（クライアント）ID | クライアントID |
| ディレクトリ（テナント）ID | テナントID |

### 2-5. 認証（リダイレクトURI）の設定

各担当者PCでのサインインを受け取るためのリダイレクトURIを登録します。

左メニューの「**認証**」をクリックします。

1. 「**プラットフォームを追加**」をクリック
2. 「**モバイルおよびデスクトップ アプリケーション**」を選択
3. 「**カスタム リダイレクト URI**」欄に `http://localhost` を入力して追加
4. 「**構成**」をクリックして保存

> クライアントシークレットの作成は不要です（このアプリは「パブリック クライアント」として登録するため、秘密情報を保持しません）。

### 2-6. API アクセス許可の設定

左メニューの「**API のアクセス許可**」をクリックします。

1. 「**アクセス許可の追加**」→「**Microsoft Graph**」→「**委任されたアクセス許可**」を選択
2. 以下のアクセス許可を追加します（検索欄で入力して絞り込む）

   | アクセス許可 | 用途 |
   |------------|------|
   | `Mail.Send` | メール送信（サインインしたユーザー自身の権限で送信） |
   | `Mail.Send.Shared` | 代理差出人アドレスからのメール送信（代理送信を使う場合） |
   | `Mail.Read` | 出欠連絡メールの読み取り（「メールから出欠を取り込む」機能を使う場合） |

3. 「**アクセス許可の追加**」をクリック
4. 可能であれば「**（テナント名）に管理者の同意を与えます**」ボタンをクリックして「はい」を選択します

> `Mail.Send`（委任）は通常ユーザー自身の同意でも利用できますが、テナントでユーザー同意が制限されている場合は管理者の同意が必須になります。念のため管理者の同意を与えておくことを推奨します。

### 2-7. 送信元メールアドレスについて

「設定」タブの「代理差出人アドレス（任意）」にアドレスを設定できます。未設定の場合は、送信操作時にサインインした Microsoft 365 アカウントのメールアドレスが送信元になります。

代理差出人を使う場合は、Entra ID のアプリに `Mail.Send.Shared`（委任）を追加して同意し、Exchange Online 側で各担当者に対象アドレスの **Send As** 権限を付与してください。権限不足の場合、送信は失敗します。

## 3. アプリの接続設定

アプリをインストール後、「**設定**」タブ →「**Microsoft 365**」で接続情報を入力します。

### 3-1. Graph API 設定

| 項目 | 入力内容 |
|------|----------|
| テナントID | [2-4](#2-4-テナントidとクライアントidを控える) で控えたテナントID |
| クライアントID | [2-4](#2-4-テナントidとクライアントidを控える) で控えたクライアントID |
| テスト送信先 | テスト送信の届け先（担当者のメールアドレスなど） |
| 代理差出人アドレス（任意） | 共通の代表アドレスなど。`Mail.Send.Shared` と Exchange Online の Send As 権限が必要 |
| テストモード | 有効にすると一斉送信のTo・CC・BCCをすべてテスト送信先へ振り替えます |

入力後「**接続テスト**」をクリックすると、Microsoft 365 のサインイン画面（ブラウザ）が表示されます。担当者本人のアカウントでサインインし、「接続に成功しました」と表示されることを確認します。  
確認できたら「**設定を保存**」をクリックします。

> サインイン結果は端末ごとに保存されるため、複数台運用の場合は **各クライアントPCで、各担当者が最初にメール送信操作（接続テストまたは実際の送信）を行った際に一度サインインが必要**です。

### 3-2. 設定ファイルについて

テナントID・クライアントID・テスト送信先・テストモード・代理差出人アドレス・確認済み認証アカウント名は、**会ごとに** `%APPDATA%\cci-mail-multi\profiles\<会ID>\app_config.json` に保存されます。クライアントシークレットは使用しません。

会の一覧（名称と接続先データベース）と前回起動した会は `%APPDATA%\cci-mail-multi\profiles.json` に保存されます。

テストモードでは、送信時にCC/BCCを空にしてテスト送信先だけを実宛先とします。本来のTo・CC・BCCはメール本文の先頭に確認情報として記載され、件名には「【テストモード】」が付きます。本番運用に戻す際は、設定タブでテストモードを解除してください。

サインイン後の認証トークンは、各PCのユーザープロファイル配下（`%USERPROFILE%\.cci-mail-multi\m365_token_cache_v2.bin`）にWindows DPAPIで暗号化された状態でキャッシュされます。認証キャッシュは**会をまたいで共有**されるため、同じアカウントで複数の会を扱う場合、サインインは端末ごとに一度で済みます。共有PCで複数の担当者が同じ Windows ユーザーでログインして使う場合、このキャッシュは共有される点に注意してください。

複数台運用の場合、`app_config.json` は **各クライアントPC・各会ごとに個別に作成**されます。  
テナントID・クライアントIDの設定変更が必要な場合は全台・全会での作業が必要です。  
会を追加する際は「設定の引き継ぎ元」で既存の会を選ぶと、これらの入力を省けます。

### 3-3. Gmail（SMTP）での送信設定

当所ドメインからのメールが宛先のGmailに届きにくい場合など、代替の送信元としてGmailを使えます。  
送信タブでは「Microsoft 365」「Gmail」を**送信のたびに選択**できるため、通常はMicrosoft 365を使い、
必要なときだけGmailに切り替える、といった運用が可能です。

#### アプリパスワードの発行

1. 送信に使うGoogleアカウント（Gmail または Google Workspace）で
   [Googleアカウントの管理](https://myaccount.google.com/) を開きます
2. 「**セキュリティ**」→「**2段階認証プロセス**」を有効にします（未設定の場合は先に設定が必要です）
3. 同じ「セキュリティ」画面から「**アプリ パスワード**」を開き、
   アプリ名（例：`cci-mail-multi`）を入力して生成します
4. 表示された16桁のパスワードを控えます（**この画面を閉じると二度と表示されません**）

> Google Workspace（組織のGmail）の場合、組織の管理者が「アプリ パスワードの生成」を許可している必要があります。無効化されている場合は組織の管理者に依頼してください。

#### アプリでの設定

「**設定**」タブ →「**Gmail**」で以下を入力します。

| 項目 | 入力内容 |
|------|----------|
| Gmailアドレス | 送信に使うGmailアドレス |
| アプリパスワード | 上記で発行した16桁のパスワード（通常のログインパスワードは使用不可） |
| テスト送信先 | テスト送信の届け先 |
| テストモード | 有効にすると一斉送信のTo・CC・BCCをすべてテスト送信先へ振り替えます |

入力後「**接続テスト**」をクリックし、「Gmailへの接続に成功しました」と表示されることを確認してから「設定を保存」をクリックします。

> Gmailアドレス・アプリパスワード・テスト送信先・テストモードは、Microsoft 365の設定と同じく
> **会ごとに** `app_config.json`（`gmail` キー）へ平文で保存されます。共有端末での取り扱いに注意してください。

#### Gmail送信を選んだ場合の違い（Microsoft 365との比較）

| 項目 | Microsoft 365 | Gmail |
|------|---------------|-------|
| 差出人 | サインインした担当者本人（代理差出人アドレス設定可） | 常に設定したGmailアドレス固定 |
| 認証 | 担当者ごとのサインイン（OAuth2、端末に記憶） | Gmailアドレス1つ分のアプリパスワード（会で共通） |
| 添付ファイルの実用上限 | 3MB | 25MB |
| 送信間隔・連続エラー中断 | あり（Microsoft 365と共通の仕様） | あり（同じ送信ワーカーを使用） |

> **注意：** Gmailで送信すると、宛先から見た差出人アドレスが当所ドメインではなくGmailアドレスになります。
> 「差出人がなりすましと誤解される」「返信が届いた担当者の個人アカウントに届く」といった影響がないか、
> 運用ルールを決めてから利用してください。

## 4. 担当者（職員）の管理

管理者権限を持つ担当者でログインすると、「**設定**」タブに「**職員管理**」タブが表示されます（一般の担当者には表示されません）。

### 職員の追加

「追加」ボタンをクリックして担当者名を入力します。  
登録した担当者名はログイン画面のドロップダウンに表示されます。

### 有効／無効の切り替え

退職者などを無効化すると、ログイン画面の選択肢から外れます。データは削除されないため、過去の送信履歴・変更履歴・受付ログの担当者名はそのまま保持されます。

### 管理者権限の切り替え

「**管理者権限 切替**」ボタンで、選択した担当者に管理者権限を付与・剥奪できます。  
管理者権限を持つ担当者のみ、「職員管理」タブと「データ管理」タブ（[10章](#10-会員データの一括削除データ管理)）を操作できます。

> 導入直後は管理者が1人もいない状態のため、最初に登録した職員に管理者権限を付与してください。

### 署名について

署名（メールの末尾に付く定型文）は担当者ごとに完全に分離されており、他の担当者の署名は管理者であっても閲覧・編集できません。各担当者が「設定」タブ→「署名管理」で自分の署名を登録します。

## 5. 役職・委員会の管理

「**設定**」タブの「**役職・委員会管理**」タブで、組織役職と委員会のマスタデータを管理します（管理者でなくても操作できます）。

### 役職の管理

組織役職（会頭・副会頭・議員など）の追加・編集・削除、表示順の並び替えができます。

### 委員会の管理

委員会（総務・運営委員会、地域経済推進委員会など）の追加・編集・削除ができます。  
所属する会員がいる委員会を削除しようとすると、所属会員数を含む確認メッセージが表示されます。削除すると、所属していた会員は「未所属」の扱いになります（会員データ自体は削除されません）。

## 5-2. 出欠連絡フォームの準備

「メールから出欠を取り込む」機能を使うには、会ごとに出欠連絡フォームと
Outlook の仕分けルールを用意します。

**フォーム自体は会ごとに別々で構いませんが、通知メールの本文書式は全会共通に揃えます。**
書式が揃っていれば、アプリ側の改修なしにどの会でも取り込めます。

```
【出欠】出席
【事業所名】株式会社○○商事
【氏名】山田 太郎
【代理役職】部長
【代理者名】鈴木 花子
【備考】途中退席します
```

作成手順・フォームの雛形・つまずいたときの対処は
[出欠連絡フォームの作り方](出欠連絡フォームの作り方.md) にまとめてあります。

> この機能には Entra ID のアクセス許可 `Mail.Read`（委任）が必要です（[2-6](#2-6-api-アクセス許可の設定)）。

## 6. データベース設定

### 6-0. 会（部会）の管理

会は「**ファイル**」→「**会を切り替える…**」で開く「会の選択」画面から管理します。

| 操作 | 内容 |
|------|------|
| 会を追加 | 会の名称と接続先データベースを登録します。既存の会から設定を引き継げます |
| 設定を編集 | 会の名称・接続先データベースを変更します |
| 登録を削除 | 一覧から会を取り除きます。**データベース本体は削除されません** |
| この会を開く | 選択した会でアプリを起動し直します |

- 起動時は**前回開いた会**が自動的に開きます。毎回選ばせたい場合は
  「起動時にこの画面を表示する」にチェックを入れてください。
- スタートメニューの「**会を選んで起動**」（`--select-profile` 付き起動）でも選択画面が出ます。
- 会の登録情報は端末ごとに保持されるため、**複数台運用では各PCで会を登録**します。
  PostgreSQLで同じ接続先を登録すれば、同じデータを共有できます。

> **会を削除してもデータは消えません。** 削除されるのは「その会を開くための登録」だけです。
> データを完全に消す場合は、SQLiteならファイルを、PostgreSQLならデータベースを個別に削除してください。

### 6-1. 接続方式の選択

「**設定**」タブの「データベース接続」で、**いま開いている会**の接続先を切り替えます。
画面上部に編集中の会の名称が表示されます。他の会の接続先は変わりません。

| 選択肢 | 用途 | 特徴 |
|--------|------|------|
| SQLite（ローカル・1台用） | 1台のPCで使用する場合 | ファイル1つで管理 |
| PostgreSQL（ネットワーク・複数台用） | 複数台から同時アクセスする場合 | サーバーPCの構築が必要 |

### SQLite の場合

データファイルは既定で `%APPDATA%\cci-mail-multi\data\<会の名称>.db` に作成されます。  
場所は設定タブの「データベース接続」→「SQLite設定」で確認・変更できます。  
**会ごとに別のファイル**を指定してください（同じファイルを複数の会に指定するとデータが混ざります）。

### PostgreSQL の場合

接続先のホスト名・ポート・データベース名・ユーザー名・パスワードを入力して「接続テスト」→「設定を保存（要再起動）」をクリックします。  
**会ごとに別のデータベース名**（例：`cci_mail_josei`、`cci_mail_seinen`）を指定してください。

#### データベースをアプリから作成する

会を追加するたびに、サーバー側にその会用のデータベースを作成する必要があります。  
pgAdmin を開かずに、アプリの「**データベースを作成**」ボタンから作成できます。

1. ホスト・ポート・データベース名・ユーザー名・パスワードを入力する
2. 「**データベースを作成**」をクリックする
3. 確認画面で「はい」を選ぶ

「接続テスト」でデータベース未作成が判明した場合も、その場で作成するか確認されます。

> 作成時のエンコーディング・ロケールは指定せず、サーバーの既定（`template1`）に従います。  
> pgAdmin の「Create Database」を既定設定で実行した場合と同じ結果になります。

> **接続ユーザーにデータベース作成権限（CREATEDB）が必要です。**  
> `postgres` ユーザーであれば権限があります。権限がない場合はエラーが表示されるので、
> 権限のあるユーザーで実行するか、pgAdmin 等で作成してください。

## 7. 複数台運用（PostgreSQL）の構築

複数の職員PCから同時にアクセスするには PostgreSQL を使います。  
1台をサーバーPC（データ保管専用）として使用します。

### 7-1. サーバーPC の選定

- 常時起動しているPC（できれば専用機）が理想です
- 固定IPアドレスを設定しておきます

### 7-2. PostgreSQL のインストール

サーバーPC で作業します。

1. [https://www.postgresql.org/download/windows/](https://www.postgresql.org/download/windows/) からインストーラーをダウンロード
2. インストーラーを実行し、画面に従ってインストール
   - **ポート番号** はデフォルト（`5432`）のままにする
   - **スーパーユーザー（postgres）のパスワード** を設定して控えておく
3. インストール完了後、「スタートメニュー」→「PostgreSQL」→「pgAdmin 4」で管理できます

### 7-3. データベースとユーザーの作成

サーバーPC でコマンドプロンプト（管理者）を開いて実行します。

```
psql -U postgres
```

パスワードを入力後、以下を順番に実行します（`パスワード` の部分は任意の文字列に変更）：

```sql
CREATE DATABASE cci_mail;
CREATE USER cci_user WITH PASSWORD 'パスワード';
GRANT ALL PRIVILEGES ON DATABASE cci_mail TO cci_user;
\q
```

### 7-4. ファイアウォールの設定（サーバーPC）

他のPCから接続できるように、Windows ファイアウォールでポートを開放します。

1. 「スタート」→「Windows Defender ファイアウォール」→「詳細設定」を開く
2. 「受信の規則」→「新しい規則」をクリック
3. 「**ポート**」を選択 → 次へ
4. 「**TCP**」「**特定のローカルポート：`5432`**」を選択 → 次へ
5. 「**接続を許可する**」→ 次へ → 次へ
6. 名前に「PostgreSQL」と入力 → 完了

### 7-5. PostgreSQL のリモート接続を許可する（サーバーPC）

PostgreSQL の設定ファイルを編集します。

**pg_hba.conf を開く：**

```
C:\Program Files\PostgreSQL\16\data\pg_hba.conf
```
（バージョン番号 `16` は実際のものに読み替えてください）

ファイル末尾に以下の行を追加します（`192.168.1.0/24` は社内ネットワークのアドレスに変更）：

```
host    all             all             192.168.1.0/24          scram-sha-256
```

**postgresql.conf を開く：**

```
C:\Program Files\PostgreSQL\16\data\postgresql.conf
```

`listen_addresses` の行を探し、以下に変更します：

```
listen_addresses = '*'
```

設定後、PostgreSQL サービスを再起動します：

```
スタートメニュー → PostgreSQL 16 → Reload Configuration
```

または管理者コマンドプロンプトで：

```
net stop postgresql-x64-16
net start postgresql-x64-16
```

### 7-6. 各クライアントPC での設定

アプリの「設定」タブ → 「データベース接続」→「PostgreSQL（ネットワーク・複数台用）」を選択し、以下を入力します。

| 項目 | 入力内容 |
|------|----------|
| ホスト名 / IPアドレス | サーバーPCのIPアドレス（例：`192.168.1.20`） |
| ポート番号 | `5432` |
| データベース名 | `cci_mail` |
| ユーザー名 | `cci_user`（手順 7-3 で作成したもの） |
| パスワード | 手順 7-3 で設定したパスワード |

「接続テスト」→ 成功を確認 → 「設定を保存（要再起動）」→ アプリを再起動

### 7-7. 既存のPostgreSQLと共存させる場合（専用インスタンスを別ポートで構築）

サーバーPCに他のアプリ用のPostgreSQLが既にインストールされている場合、**同じポート（5432）に相乗りさせない**でください。  
他アプリのバージョンアップ・アンインストール・設定変更（`postgresql.conf` や `pg_hba.conf` の変更、リソース競合など）に cci_mail 側が巻き込まれるリスクがあるためです。

代わりに、**別ポート（例：`5433`）で cci_mail 専用の PostgreSQL インスタンスをもう一つインストール**し、完全に分離して運用します。1台のPC上に複数の独立した PostgreSQL インスタンスを同時稼働させることは問題ありません。

#### ① ポートの空き確認

サーバーPC以外のPCから、候補ポート（例：`5433`）が未使用であることを確認します。

```powershell
Test-NetConnection -ComputerName <サーバーPCのIP> -Port 5433
```

`TcpTestSucceeded : False` であれば未使用です。

#### ② cci_mail専用インスタンスをインストール（サーバーPC）

[https://www.postgresql.org/download/windows/](https://www.postgresql.org/download/windows/) からインストーラーをダウンロードし、既存インスタンスとは別のインストール先・データディレクトリ・ポート・サービス名を指定してインストールします。

コマンドプロンプト（管理者）で無人インストールする場合：

```
postgresql-17.x-windows-x64.exe --mode unattended ^
  --unattendedmodeui minimal ^
  --superpassword "スーパーユーザーパスワード" ^
  --serverport 5433 ^
  --prefix "C:\PostgreSQL\17-cci_mail" ^
  --datadir "C:\PostgreSQL\17-cci_mail\data" ^
  --servicename "postgresql-cci_mail" ^
  --servicepassword "スーパーユーザーパスワード"
```

GUIでインストールする場合は、インストール先・データディレクトリ・ポート番号の入力欄に上記の値を指定してください。

#### ③ データベースの作成

```
"C:\PostgreSQL\17-cci_mail\bin\psql.exe" -U postgres -p 5433 -c "CREATE DATABASE cci_mail;"
```

#### ④ リモート接続の許可

**このインスタンス専用の** `postgresql.conf`（例：`C:\PostgreSQL\17-cci_mail\data\postgresql.conf`）を編集：

```
listen_addresses = '*'
```

**このインスタンス専用の** `pg_hba.conf`（例：`C:\PostgreSQL\17-cci_mail\data\pg_hba.conf`）に追記（社内ネットワークのアドレス範囲に合わせて変更）：

```
host    all             all             192.168.10.0/24         scram-sha-256
```

> 既存インスタンスの `postgresql.conf` / `pg_hba.conf` には触れないでください。

#### ⑤ ファイアウォールの設定（新しいポート用）

```
netsh advfirewall firewall add rule name="PostgreSQL cci_mail (5433)" dir=in action=allow protocol=TCP localport=5433
```

#### ⑥ サービスの再起動

```
net stop postgresql-cci_mail
net start postgresql-cci_mail
```

#### ⑦ 各クライアントPCでの設定

[7-6](#7-6-各クライアントpc-での設定) と同じ手順で、**ポート番号のみ `5433`** に変更して接続します。

| 項目 | 入力内容 |
|------|----------|
| ホスト名 / IPアドレス | サーバーPCのIPアドレス |
| ポート番号 | `5433` |
| データベース名 | `cci_mail` |
| ユーザー名 | `postgres`（または作成した専用ユーザー） |
| パスワード | ②で設定したパスワード |

「接続テスト」→ 成功を確認 → 「設定を保存（要再起動）」→ アプリを再起動

## 8. サーバーPCを入れ替えるとき

### A. SQLite（1台用）の場合

PC を変えるときは、**会ごとの**データファイルをコピーします。

1. **旧PCで** 会ごとのデータファイルの場所を確認する
   （設定タブ →「データベース接続」→「SQLite設定」。既定は `%APPDATA%\cci-mail-multi\data\<会の名称>.db`）
2. 使用しているすべての会の `.db` ファイルをUSBメモリや共有フォルダ経由でコピーする
3. **新PCに** アプリをインストールし、`.db` ファイルを同じ場所（または任意の場所）に配置する
4. 新PCで「ファイル」→「会を切り替える…」→「会を追加」から、会ごとに名称と
   コピーした `.db` ファイルのパスを登録する
5. 各会を開いて名簿・テンプレート・送信履歴が表示されれば完了

> Microsoft 365の接続情報は端末ごとの設定のため引き継がれません。
> 新PCでは会ごとに設定タブから入力し直してください
> （2つ目以降の会は「設定の引き継ぎ元」で省略できます）。

### B. PostgreSQL（複数台用）の場合

#### 全体の流れ

```
① 旧サーバーのデータをバックアップ
     ↓
② 新サーバーに PostgreSQL をインストール・設定（手順 7-2〜7-5）
     ↓
③ バックアップデータを新サーバーに復元
     ↓
④ 各クライアントPCの接続先を変更（手順 7-6）
     ↓
⑤ 全台で動作確認 → 旧サーバー停止
```

#### ① データのバックアップ（旧サーバーPC）

コマンドプロンプト（管理者）で実行します：

```
pg_dump -U postgres -Fc cci_mail > C:\backup\cci_mail_backup.dump
```

- `-U postgres` はPostgreSQLのスーパーユーザー名（変更している場合は読み替え）
- パスワードを求められたら入力
- `C:\backup\` フォルダがない場合は先に作成してください

バックアップファイル（`cci_mail_backup.dump`）をUSBメモリや共有フォルダにコピーします。

#### ② 新サーバーのセットアップ

[7-2](#7-2-postgresql-のインストール) 〜 [7-5](#7-5-postgresql-のリモート接続を許可するサーバーpc) の手順でインストール・設定します。

#### ③ データの復元（新サーバーPC）

バックアップファイルを新サーバーにコピーした後、コマンドプロンプト（管理者）で実行します：

```
pg_restore -U postgres -d cci_mail C:\backup\cci_mail_backup.dump
```

「処理が正常に完了しました」と表示されれば復元完了です。

> 出欠状況HTML出力先パス（[9章](#9-出欠状況html出力の設定)）はPostgreSQLモードではデータベース内に保存されているため、この復元手順に含まれます。別途の再設定は不要です。

#### ④ 各クライアントPCの接続先変更

[7-6](#7-6-各クライアントpc-での設定) の手順で全台の接続先を新サーバーのIPアドレスに変更します。

#### ⑤ 動作確認

全クライアントPCで以下を確認します：

- [ ] 名簿管理タブに会員一覧が表示される
- [ ] 会議管理タブに会議一覧が表示される
- [ ] 送信履歴タブに履歴が表示される
- [ ] 受付タブで複数PCから同時に操作できる

全台で確認できたら旧サーバーを停止して構いません。

## 9. 出欠状況HTML出力の設定

「**設定**」タブの「**出力設定**」タブで、会議の出欠状況をHTMLファイルとして自動出力する機能を設定します。

- 「出力先ファイル」に保存先パスを指定します（例：`\\server\share\出欠状況.html`）。共有フォルダを指定すると、他のPCのブラウザからもリアルタイムに近い形で出欠状況を確認できます
- 空白のままにするとHTML出力は行われません
- 受付タブでの操作のたびに自動更新されるほか、「今すぐ出力」ボタンで手動出力もできます

### PostgreSQLモード（複数台運用）での共有について

v1.1.5以降、PostgreSQLモードでは出力先パスの設定がデータベース経由で **全端末に共有** されます（いずれかの端末で設定すれば、他の端末でも同じ設定が使われます）。  
SQLiteモード（1台運用）では、この設定は端末ごとの個別設定（ローカル設定ファイル）のままです。

## 10. 会員データの一括削除（データ管理）

管理者権限を持つ担当者でログインすると、「**設定**」タブに「**データ管理**」タブが表示されます。

「会員データ一括削除（開発用）」機能は、全会員データ（会員本体・メールアドレス・変更履歴）に加え、設定タブで管理している組織役職・委員会のマスタ、会議・出欠記録・受付ログ、送信履歴（送信ジョブ・送信ログ）まで、テストで作成したデータをすべて完全に削除するものです。**取り消しはできません。**

> ラベルのとおり開発・テスト環境の初期化を想定した機能です。本番運用中のデータベースに対して実行すると、名簿・出欠・履歴のすべてが失われます。実行が必要な特別な事情がある場合は、必ず事前にバックアップ（[11章](#11-バックアップ)）を取ってから、内容をよく確認した上で操作してください。

実行するには確認ダイアログで「はい」を選んだ後、さらに「DELETE」という文字列の入力を求められます（二段階の確認）。

## 11. バックアップ

### SQLite の場合

会ごとの `.db` ファイル（既定：`%APPDATA%\cci-mail-multi\data\` 配下）をそのままコピーします。  
**使用しているすべての会の分**を対象にしてください。フォルダごとコピーするのが確実です。  
定期的に外付けHDDや共有フォルダに保存することをお勧めします。

**バックアップのタイミング（目安）：**
- 重要な名簿更新作業の前後
- 月次（最低限）

### PostgreSQL の場合

以下のコマンドを定期実行するスクリプトを作成して、タスクスケジューラに登録することをお勧めします。

```bat
@echo off
set PGPASSWORD=パスワード
set BAK_DIR=C:\backup\cci_mail
if not exist %BAK_DIR% mkdir %BAK_DIR%
set FNAME=%BAK_DIR%\cci_mail_%date:~0,4%%date:~5,2%%date:~8,2%.dump
pg_dump -U postgres -Fc cci_mail > %FNAME%
echo バックアップ完了: %FNAME%
```

7世代分（1週間）を残すなど、古いファイルの削除ロジックも追加することをお勧めします。

## 13. トラブルシューティング

### メール送信が失敗する

**確認項目：**
1. 設定タブの「接続テスト」を実行し、サインイン画面が表示されたら担当者本人のアカウントでサインインし直す
2. API アクセス許可（委任）に `Mail.Send` が付与されているか確認する（Entra ID → アプリの登録 → API のアクセス許可）
3. インターネット接続を確認する
4. 送信元として代表メールアドレス（共有メールボックス）を使いたい場合、担当者のアカウントにそのメールボックスへの「Send As」権限が付与されているか確認する（Exchange 管理者に確認）

### メール送信のたびにサインインを求められる／認証が切れる

担当者のMicrosoft 365アカウントのパスワード変更・多要素認証設定の変更・長期間未使用などにより、端末にキャッシュされた認証が無効になることがあります。この場合、次回の送信操作時に再度サインイン画面が表示されるので、通常どおりサインインすれば復旧します。特別な管理者作業は不要です。

> v1.1.15以降、認証トークンキャッシュのファイル形式が変わりました（[3-2](#3-2-設定ファイルについて)参照）。v1.1.14以前からの更新時、旧ファイル（`m365_token_cache.bin`）は初回起動時に自動的に削除され、新しい暗号化キャッシュに切り替わります。担当者は通常どおり一度サインインすれば復旧するため、特別な対応は不要です。

### 一斉送信が「連続してエラーが発生したため中断しました」と表示されて途中で止まる

Microsoft 365への通信エラーなどが5件連続で発生すると、大量のエラー送信を防ぐため自動的に送信を中断する仕様です（v1.1.15以降）。以下を確認してください。

1. インターネット接続が安定しているか
2. Microsoft 365 側で障害が発生していないか（[Microsoft 365 サービスの状態](https://portal.office.com/servicestatus)）
3. 担当者の認証が切れていないか（上記「メール送信のたびにサインインを求められる」を参照）

原因を解消した後、未送信だった宛先を選び直して再送信してください（中断前に送信できなかった宛先は「送信履歴」にスキップとして記録されています）。

### 送信に時間がかかるようになった

v1.1.15以降、Microsoft 365の送信件数制限（レート制限）に抵触しないよう、宛先ごとに約2秒の送信間隔を自動的に空けるようになりました。150件の一斉送信であれば概ね5分程度が目安です。仕様どおりの動作であり、異常ではありません。

### PostgreSQL に接続できない（「接続テスト失敗」）

**確認項目：**
1. サーバーPCの電源が入っているか
2. サーバーPC で PostgreSQL サービスが起動しているか
   - タスクマネージャー → サービス → `postgresql-x64-16` が「実行中」か
3. Windows ファイアウォールでポート 5432 が許可されているか（[7-4](#7-4-ファイアウォールの設定サーバーpc)）
4. `pg_hba.conf` の設定が正しいか（[7-5](#7-5-postgresql-のリモート接続を許可するサーバーpc)）
5. ホスト名/IP・ユーザー名・パスワードが正しいか

### アプリが起動しない

1. デスクトップのショートカットを右クリック→「プロパティ」でインストール先を確認
2. インストール先フォルダに `CCIMailMulti.exe` があるか確認
3. 一度アンインストールして再インストールする

### 「担当者名が表示されない」（ログイン画面）

設定タブ → 職員管理（[4章](#4-担当者職員の管理)）で担当者を追加してください。「職員管理」タブが見当たらない場合は、ログイン中の担当者に管理者権限が付与されていません。他の管理者に依頼するか、導入直後で管理者が誰もいない場合は開発担当者に相談してください。

**担当者は会ごとに登録します。** 別の会に切り替えた直後は担当者が未登録のため、
ログイン画面の「職員を追加」で最初の担当者（管理者）を登録してください。

### 起動したら意図しない会が開く

前回開いた会が自動的に開く仕様です。「ファイル」→「会を切り替える…」で目的の会を選び直してください。
以降はその会が記憶されます。起動のたびに選びたい場合は、会の選択画面で
「起動時にこの画面を表示する」にチェックを入れてください。

### 別の会のデータが混ざって見える

複数の会に同じ接続先（同じ `.db` ファイル、または同じPostgreSQLデータベース名）を
登録していないか確認してください。会ごとに別の接続先を指定する必要があります。

### 他の担当者の署名が編集できない・見えない

仕様どおりの動作です。署名は担当者ごとに完全に分離されており、管理者であっても他の担当者の署名は閲覧・編集できません（[4章](#4-担当者職員の管理)）。

### 新サーバーPCのIPアドレスを確認するには

新サーバーPC でコマンドプロンプトを開き `ipconfig` を実行します。  
`IPv4 アドレス` に表示される数字（例：`192.168.1.20`）がIPアドレスです。  
IPアドレスが変わらないよう、新サーバーPCには **固定IPアドレス** を設定することをお勧めします。
